# Output Standards

## Evidence levels
Label important findings when useful:
- **Observed:** directly visible in code/runtime/docs.
- **Maintainer-stated:** explicitly explained by maintainers.
- **Inferred:** engineering interpretation supported by evidence.
- **Hypothesis:** requires verification.

## Pattern quality bar
A pattern must contain context, problem, forces, solution, consequences, failure modes, when-to-use, when-not-to-use and evidence.

## Decision quality bar
Technology recommendations must state selection conditions, rejection conditions, alternatives, operational burden and unresolved validation work.

## Writing standard
Use concise technical prose. Avoid feature-list summaries. Prefer diagrams/tables only when they clarify structure or comparison. Preserve source references in notes.

## Repository review scorecard
Score only after evidence collection: architecture clarity, extensibility, reliability mechanisms, observability, security/isolation, deployment maturity, ecosystem/maintenance, developer experience, enterprise fit. Scores must include rationale; never aggregate into a meaningless popularity score.
